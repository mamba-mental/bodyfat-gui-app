BODYFAT APP - STORAGE INCONSISTENCY INVESTIGATION REPORT
VERBAL SUMMARY FOR TEXT-TO-SPEECH

========================================
EXECUTIVE SUMMARY
========================================

Your hypothesis is CONFIRMED.

The bodyfat app is simultaneously using THREE different storage systems:
1. Redis (in-memory cache)
2. SQLite database 
3. JSON files

This is causing data inconsistency because entries are saved in different locations depending on which code path executes.

========================================
DETAILED FINDINGS
========================================

STORAGE SYSTEM 1: REDIS
- Location: src/lib/redis.ts
- Status: Fully implemented with dedicated API routes
- Available: Only in development mode, NOT in production
- Problem: This is essentially abandoned code that exists but isn't actually used by the main application

STORAGE SYSTEM 2: SQLITE
- Location: data/bodyfat.db (14.1 megabytes)
- Used by: Python API running on port 8000
- Contains: Proper database tables for users, entries, reports, and calculations
- Status: Active in both development and production

STORAGE SYSTEM 3: JSON FILES
- Location: data/apexfit-data.json
- Used by: Next.js application routes
- Strategy: JSON writes first, then syncs with SQLite as backup
- Problem: Creates duplicate data and potential conflicts

========================================
HOW DATA IS CURRENTLY SAVED
========================================

When you save an entry, here's what happens:

Step 1: The Next.js app writes to the JSON file first (fast, local storage)
Step 2: Then it attempts to sync with the Python API's SQLite database
Step 3: If there are conflicts, data reconciliation code tries to merge the differences
Step 4: Redis exists but is NOT called by the main application routes

This multi-step process explains why your entries are inconsistent.

========================================
CRITICAL PROBLEMS
========================================

Problem 1: NO SINGLE SOURCE OF TRUTH
- Data exists in three places simultaneously
- No clear hierarchy of which storage is authoritative
- Merge logic can create unexpected results

Problem 2: DEVELOPMENT VERSUS PRODUCTION MISMATCH
- Development has Redis available
- Production does NOT have Redis
- Code written for Redis in dev will fail in production

Problem 3: RACE CONDITIONS
- If the Python API fails, data gets saved to JSON but not SQLite
- This creates permanent inconsistency between the two stores

Problem 4: ABANDONED CODE
- The Redis implementation at /api/redis is fully functional but never called
- This is dead code taking up space and causing confusion

========================================
RECOMMENDED SOLUTION
========================================

CONSOLIDATE TO SQLITE AS SINGLE SOURCE OF TRUTH

Why SQLite:
- Already in production and working
- Proper database schema with relationships
- Supports atomic transactions
- Better query performance
- Production-ready

- Create script to read data/apexfit-data.json
